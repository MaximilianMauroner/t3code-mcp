## Bounded live inventory

`t3_threads_list` uses numeric offsets into a fresh live list on each call.
With `sort=recent`, activity can move an unread thread before the next offset.
One completed walk plus ID deduplication can miss it, even when totals match.
The public list has no supported snapshot or as-of pin.

Before the first page, set a finite combined page and elapsed-time budget for
the walk, rescan and reconciliation. Keep authorized filters and page size fixed.
Honor the core's lifecycle exclusions and read-only restrictions throughout.

1. Walk from the initial cursor until no next cursor remains or the budget ends.
   Retain each page's cursors, page count, stable IDs, observation times, total
   and relevant returned source update timestamps in bounded redacted evidence.
2. After a complete walk, recheck connection/readiness and perform one full
   rescan from the initial cursor with the same filters, within the same budget.
   Retain each walk's IDs and their stable-ID union. Compare IDs, counts, totals,
   order and update timestamps; reconcile differences against the retained
   observations and read allowed details/ranges for newly observed IDs.
   Do not start further scans or mutate shared threads to stabilize the list.
3. If the budget ends, churn persists or differences remain unreconciled, record
   the inventory/history gap and excluded coverage; do not claim exhaustive
   coverage. Even matching ID counts and two matching scans support only
   time-bounded observed inventory, not an atomic snapshot or complete history.
