# Security and access risks

[Back to README](../README.md)

**Treat write access to this MCP as access to your T3 coding agent, with the machine permissions that agent has.** A caller can ask it to run commands, read files, change code, or send data elsewhere if T3 and the provider permit those actions. The absence of a direct terminal tool does not prevent this indirect access. The affected machine is wherever the T3 agent executes, which may be your PC or a separate server; this does not automatically grant root access.

The gateway has useful protections: HTTP binds to loopback by default, `/mcp` rejects missing or incorrect bearer credentials, token comparison uses `timingSafeEqual`, request bodies are capped at 2 MiB, and mutations check read-only mode and T3's `orchestration:operate` scope. These controls do not make it a sandbox or a service suitable for mutually untrusted users. The following findings come from a source review of this implementation, not a penetration test or a security certification.

| Possible problem | What it means in this implementation | How to reduce the risk |
| --- | --- | --- |
| **Agent tasks can affect the host** | New threads default to `runtimeMode: "full-access"`. Both creation and sending accept a caller-selected runtime mode. `MCP_READ_ONLY` defaults to `false` in code, although deployment examples set it to `true`. A compromised authorized client could submit destructive tasks or tasks that expose secrets, subject to upstream permissions. | Start read-only. Run T3 agents under a dedicated unprivileged account or isolated environment with restricted files, credentials, and network access. Enforce permission limits upstream; asking the client to select `approval-required` is not an enforced gateway policy. |
| **The client can approve its own requests** | `t3_pending_action_respond` forwards approval decisions without independently verifying a human. An assistant with write access can submit work and answer the resulting approval request. Tool annotations are descriptive hints, not authorization controls. | Use a trusted client with explicit human review, and enforce critical approval restrictions outside the same client's control. |
| **One leaked token grants the same gateway access as yours** | HTTP uses one static bearer token, with no built-in expiry, per-client revocation, user identity, or role separation. Token strength is not validated. All callers share the configured T3 credential and global read-only setting. Stdio relies on the local host's process access rather than bearer authentication. | Use a long random token distinct from the T3 token. Keep credentials out of chats and logs. Rotate a leaked token and restart the gateway; use separate deployments and suitably restricted upstream credentials for different trust levels. |
| **No per-project or workspace boundary** | There is no gateway allowlist for projects, threads, or filesystem roots. Search filters are not access controls. Project registration accepts a workspace path and can request directory creation; thread creation accepts a worktree path. T3 decides which paths and resources are allowed. | Expose only a T3 environment intended for this client, and enforce filesystem isolation on the agent host. Do not treat a selected project as confinement to that folder. |
| **Read-only still exposes private data** | Read tools return project paths, thread messages, agent responses, plans, and pending-action details available to the upstream credential. This content can contain source code or secrets and may reach the MCP client's model provider or logs. Text truncation is not secret redaction; upstream error messages are also forwarded without a general redaction layer. | Connect only trusted clients, review their data handling, and limit what the upstream environment contains. Read-only prevents gateway mutations, not disclosure. |
| **Prompt injection or a mistaken request can trigger real actions** | Repository text and agent messages can contain instructions that influence the connected assistant. The gateway validates tool arguments but cannot determine whether a valid task reflects your intent. Voice transcription and ambiguous project names add another source of mistakes. | Require review of the resolved target and consequential actions in the client. Use upstream isolation to limit damage even when the assistant makes a valid but unwanted call. |
| **Remote HTTP can expose tokens and content** | The listener serves plain HTTP, and the upstream URL also permits HTTP. Binding to `0.0.0.0` or forwarding the port increases reachability. The transport does not configure Host/Origin allowlists or enable the SDK's DNS-rebinding protection. Bearer authentication still applies; these omissions alone do not demonstrate an authentication bypass. | Keep the listener on loopback behind a correctly configured authenticated tunnel or HTTPS proxy. Protect the gateway-to-T3 hop too when it crosses machines. Configure allowed hosts/origins at the boundary. |
| **A tunnel adds another trusted access boundary** | The included launcher injects the gateway bearer header for forwarded requests. The gateway therefore relies on the tunnel's external access controls to decide who can reach that authenticated connection. `/healthz` is unauthenticated and reveals the service name. | Verify tunnel sharing and account access, protect its runtime key, and check who can invoke the remote endpoint. A working tunnel does not establish that its access policy is correct. |
| **Resource exhaustion and unexpected costs** | There are no application-level request-rate limits, concurrency quotas, or agent spending limits. Authenticated callers can repeatedly poll or start work. The journal retains operations indefinitely and rewrites the full JSON file on updates. | Add proxy limits, provider budgets, disk monitoring, and an operational retention policy that preserves needed retry records. The body-size cap does not limit total traffic or task cost. |
| **Local compromise and incomplete audit records** | Credentials live in process environments and operator-managed files. Journal files use mode `600`, but contain IDs, caller-supplied idempotency keys, and error strings. The journal is not a per-user security audit trail. Systemd hardening of the gateway does not sandbox agents running in a separate T3 service. | Protect env files and the data directory, avoid secrets in idempotency keys, and isolate service accounts. Add access logging at the trusted boundary if caller attribution is required. |

If access is compromised, disable the remote route and rotate the affected MCP, tunnel, and T3 credentials as appropriate. Inspect T3 for running tasks and verify they have stopped: disconnecting the MCP client or stopping the gateway does not cancel work already accepted by T3. Review files and credentials the agent could access.
